# Live review: the 144 commands added by Tier 1 + Tier 2

Prompt for a session running on a **local machine with an authenticated
standalone OpenStack cloud that may be freely modified**. It covers branch
`claude/ironic-coverage-tier-plan-4h7zhh` at the commit that closes Tier 2.

Unlike `2026-08-08-tier-plan-probe.md`, this run is **write-heavy by design**.
Every command below creates, changes or deletes something, and that is the
point: the offline tests pin request shapes against mock servers built from the
API source, so what is left to learn is whether the real services accept those
requests and whether the rendered output is right.

Scope: the **144 leaf commands** this branch added (403 → 547). They are listed
per section. Nothing outside that list needs re-checking.

```sh
git fetch origin claude/ironic-coverage-tier-plan-4h7zhh

**Record the cloud's release once**, at the top of your report — every later

```

`koc` supports **Zed (2022.2) and newer**. If this cloud is newer than Zed, a
PASS here does not prove the command works on Zed — say which release you ran
against so the result can be scoped.

## Rules for this run

- **Nothing from this run gets committed.** Endpoints, host names, project and
  user UUIDs, server names, tokens and `--debug` captures are private data and
  the repo is public (AGENTS.md → "Private data never leaves the org"). Report
  *findings* — "identical to OSC", "400, neutron wants `foo` not `bar`",
  "renders an empty table where OSC prints 3 rows" — and keep the evidence in
  the conversation. Redact host names yourself; `--debug` redacts tokens but not
  hostnames.
- **Compare against upstream OSC wherever it is installed.** `openstack <same
  command> -f json` beside `./koc <command> -f json` is the strongest signal
  available. Where the two differ, quote both and say which one matches the API
  response.
- **Every section cleans up after itself.** Run the teardown even when a check
  fails — a half-built fixture makes the next section's failures ambiguous.
- **A crash, a Go panic, a nil deref or a message that names a Go type is a bug
  regardless of the API's answer.** Note it separately from API-level failures.
- **Do not fix anything in this run.** Collect findings; the fixes are a
  separate commit on the same branch with tests.

Use a dedicated project if the cloud has more than one. Prefix everything you
create with `kocrev-` so a stray resource is obvious later.

## §2 — Compute state verbs and server groups (18 commands)

`server shelve/unshelve/rescue/unrescue`, `server image create`,
`server add/remove port|network|fixed ip`, `server group create/delete/list/show`,
`availability zone list`, `limits show`, `usage list/show`.

Needs one disposable server. Build it, then:

```sh
./koc server group create kocrev-sg --policy anti-affinity
./koc server group show kocrev-sg
./koc server group list
```

Check `server group show` prints **`policy` + `rules`** on a cloud at
microversion ≥ 2.64 and the older `policies` array below it. Whichever shape the
cloud returns, the rendered output must not be empty — that is the exact bug the
2.64 split introduces.

```sh
./koc server shelve kocrev-vm --wait
./koc server show kocrev-vm -c status          # SHELVED_OFFLOADED
./koc server unshelve kocrev-vm --wait
./koc server rescue kocrev-vm
./koc server unrescue kocrev-vm
./koc server image create kocrev-vm --name kocrev-snap --wait
```

`server unshelve --host` requires nova **2.91**. On an older cloud it must fail
with a clear microversion message, and — this is the part worth checking — a
plain `unshelve` with no flags must send a body nova <2.77 accepts (the inner
object is materialised only when there is a field to put in it). Run plain
`unshelve` with `--debug` and confirm the body is `{"unshelve": null}`.

```sh
./koc server add port kocrev-vm <port>
./koc server remove port kocrev-vm <port>
./koc server add network kocrev-vm <network>
./koc server remove network kocrev-vm <network>
./koc server add fixed ip kocrev-vm <network>
./koc server remove fixed ip kocrev-vm <ip>
```

`server add port --tag` needs nova **2.49**; check the tag actually lands
(`./koc server show <vm> -f json` or `openstack port show <port>`).

Cross-service reads:

```sh
./koc availability zone list            # nova + cinder + neutron merged
./koc availability zone list --compute
./koc limits show --absolute
./koc limits show --rate
./koc usage list --start 2026-07-01 --end 2026-08-01
./koc usage show --start 2026-07-01 --end 2026-08-01
```

`usage show` is the one to watch: the single-tenant body is one object, not an
array, and the naive pagination path returns nil. It must print a populated row,
not an empty table and not a panic.

`server password show` is koc-native — `nova get-password`, which OSC never
ported — so there is nothing to diff it against. Boot a server with an RSA
keypair whose private half you hold and whose image runs a guest agent that
generates a password (a Windows/cloudbase-init image is the real case):

```sh
./koc server password show kocrev-vm                          # base64 ciphertext
./koc server password show kocrev-vm --private-key <key.pem>  # decrypted
./koc server password show kocrev-vm --private-key - < <key.pem>
```

Cross-check the decryption against nova's own documented recipe:

```sh
./koc server password show kocrev-vm -f value -c password \
  | base64 -d | openssl pkeyutl -decrypt -inkey <key.pem>
```

Check that a server with no stored password gives the "guest agent has not
posted one" message rather than a blank row, that an OpenSSH-format key is
named as such (with the `ssh-keygen -p -m PEM` fix) rather than "invalid key",
and that a bad `--private-key` path fails **before** any API call.

Teardown: delete the snapshot, the server group, and the server.

## §3 — Volume: transfers, QoS, metadata (17 commands)

`volume transfer request accept/create/delete/list/show`,
`volume qos associate/create/delete/disassociate/list/set/show/unset`,
`volume snapshot set/unset`, `volume backup set/unset`.

```sh
./koc volume create kocrev-vol --size 1
./koc volume transfer request create kocrev-vol --name kocrev-xfer
./koc volume transfer request list
./koc volume transfer request show kocrev-xfer
./koc volume transfer request delete kocrev-xfer
```

`--no-snapshots` needs cinder **3.55** and posts to `/volume-transfers`, a
different endpoint from the pre-3.55 `/os-volume-transfer`. Run it with
`--debug` and confirm the URL changes; on a cloud below 3.55 it must say so
rather than 404.

Accepting a transfer needs a second project. If you have one, accept it there
and confirm the volume moved; if not, say so — do not fake it.

```sh
./koc volume qos create kocrev-qos --consumer front-end --property read_iops_sec=100
./koc volume qos set kocrev-qos --property write_iops_sec=200
./koc volume qos show kocrev-qos
./koc volume qos associate kocrev-qos <volume-type>
./koc volume qos list
./koc volume qos disassociate kocrev-qos --volume-type <volume-type>
./koc volume qos unset kocrev-qos --property read_iops_sec
./koc volume qos delete kocrev-qos
```

`qos unset` is the sharp edge: cinder's PUT **merges** rather than replaces, so
`koc` deletes the survivors first. Confirm with `qos show` that the removed key
is gone **and** the others are still there.

```sh
./koc volume snapshot create kocrev-vol --name kocrev-snap
./koc volume snapshot set kocrev-snap --property a=1 --description "review"
./koc volume snapshot unset kocrev-snap --property a
./koc volume backup create kocrev-vol --name kocrev-bk   # if cinder-backup runs
./koc volume backup set kocrev-bk --description "review"
./koc volume backup unset kocrev-bk --property a
```

`volume backup set` exercises a gophercloud bug this branch works around —
upstream sends an unwrapped body and cinder answers 400. A 400 here means the
workaround regressed.

Teardown: delete the backup, snapshot and volume.

## §5 — Placement (21 commands)

`resource class create/delete/list/set/show`, `resource provider create/set`,
`resource provider inventory set/delete`, `resource provider inventory class set`,
`resource provider trait set/delete`, `resource provider aggregate set`,
`resource provider allocation show/set/unset`, `allocation candidate list`,
`resource usage show`, `trait create/delete/show`.

Placement writes on a live cloud are **the highest-risk section here** — a bad
inventory or allocation makes nova stop scheduling. Use a **new** provider you
create yourself and never touch a compute node's provider.

```sh
./koc resource provider create kocrev-rp
RP=$(./koc resource provider list --name kocrev-rp -f value -c uuid)

./koc trait create CUSTOM_KOCREV
./koc trait show CUSTOM_KOCREV
./koc resource provider trait set $RP --trait CUSTOM_KOCREV
./koc resource provider trait delete $RP

./koc resource class create CUSTOM_KOCREV_UNIT
./koc resource class show CUSTOM_KOCREV_UNIT
./koc resource class list | grep KOCREV

./koc resource provider inventory class set $RP CUSTOM_KOCREV_UNIT --total 8
./koc resource provider inventory set $RP --resource CUSTOM_KOCREV_UNIT=16
./koc resource usage show $RP
./koc resource provider inventory delete $RP --resource-class CUSTOM_KOCREV_UNIT

./koc resource provider aggregate set $RP --aggregate <uuid>
./koc allocation candidate list --resource VCPU=1
./koc resource provider allocation show <consumer-uuid>
```

Two things to check specifically:

1. **Generation handling.** `inventory set`, `inventory class set` and
   `aggregate set` all read the provider's generation first and send it back.
   Run two in a row without re-reading and confirm neither 409s.
2. **`parent_provider_uuid` serialises as an explicit `null`** on
   `resource provider set` when un-parenting (placement 1.37). Check with
   `--debug` that the key is present and null, not omitted.

Teardown: delete the allocations you set, then the provider, the resource class
and the trait (custom traits and classes are deletable; standard ones are not —
confirm the error is clear if you try).

## §6 — Neutron extensions (31 commands)

`address scope`/`address group` (11), `ip availability` (2), `network rbac` (5),
`network segment` (5), `floating ip port forwarding` (5),
`router add/remove route` (2).

First, find out what this cloud actually has — several of these are optional
extensions and a missing one is BLOCKED, not FAIL:

```sh
./koc network extension list -f value -c Alias | sort
```

Look for `address-scope`, `address-group`, `network-ip-availability`,
`rbac-policies`, `segment`, `floating-ip-port-forwarding`, `extraroute-atomic`.

```sh
./koc address scope create kocrev-as --ip-version 4
./koc address scope set kocrev-as --no-share
./koc address scope list --no-share
./koc address scope show kocrev-as
```

`--share`/`--no-share` must both reach neutron — `shared=false` is a real filter,
not a zero value to drop. Confirm with `--debug` that
`address scope list --no-share` sends `shared=false`.

```sh
./koc address group create kocrev-ag --address 192.0.2.0/24
./koc address group set kocrev-ag --address 198.51.100.0/24
./koc address group unset kocrev-ag --address 198.51.100.0/24
./koc address group show kocrev-ag
```

Adding and removing addresses must use the `add_addresses` /`remove_addresses`
actions, not the plain update — neutron's update schema has no `addresses`
field at all. Verify with `--debug`.

```sh
./koc ip availability list
./koc ip availability show <network>          # per-subnet rows, not just totals

./koc network rbac create <network-id> --type network --action access_as_shared \
    --target-project <other-project-id>
./koc network rbac list
./koc network rbac show <id>
./koc network rbac set <id> --target-project <third-project-id>
./koc network rbac delete <id>

./koc network segment list
./koc network segment show <id>
./koc network segment create kocrev-seg --network <net> --network-type vlan \
    --physical-network <physnet> --segment 4000
./koc network segment set <id> --name kocrev-seg2
./koc network segment delete <id>
```

`segment create` needs an ML2 driver that allows the type; a 400 naming the type
is the cloud's answer, not a `koc` bug. `segment set --name` alone must not blank
the description or the segmentation ID.

```sh
./koc floating ip port forwarding create <fip-id> \
    --port <port> --internal-ip-address <ip> \
    --internal-protocol-port 22 --external-protocol-port 2222 --protocol tcp
./koc floating ip port forwarding list <fip-id>
./koc floating ip port forwarding show <fip-id> <pf-id>
./koc floating ip port forwarding set <fip-id> <pf-id> --external-protocol-port 2223
./koc floating ip port forwarding delete <fip-id> <pf-id>
```

Two specific checks: `set` with only `--external-protocol-port` must **not**
also send `protocol` (an unset `--protocol` on `set` defaults to empty, not
`tcp`); and the `--internal/external-protocol-port-range` flags must be absent
from the body when unused — neutron rejects a single port and a range together.
Both are `--debug` checks.

```sh
./koc router add route <router> --route destination=198.51.100.0/24,gateway=<ip>
./koc router show <router> -c routes
./koc router remove route <router> --route destination=198.51.100.0/24,gateway=<ip>
```

Confirm with `--debug` that these hit `/add_extraroutes` and
`/remove_extraroutes`, not a plain router PUT. If the cloud lacks
`extraroute-atomic` the calls 404 — that is the guard working, report BLOCKED.

Also re-check the Tier 1 leftovers here: `router add/remove gateway` and
`subnet unset`.

Teardown: delete the address group, address scope and anything else created.

## §7 — Network QoS (12 commands)

```sh
./koc network qos rule type list
./koc network qos rule type show bandwidth-limit
./koc network qos rule type show bandwidth_limit    # both spellings accepted
```

`rule type list` tells you which rule types this cloud supports; only test those.

```sh
./koc network qos policy create kocrev-qos --description "review"
./koc network qos policy list
./koc network qos policy show kocrev-qos
./koc network qos policy set kocrev-qos --share
./koc network qos policy set kocrev-qos --no-share

./koc network qos rule create kocrev-qos --type bandwidth-limit \
    --max-kbps 1000 --max-burst-kbits 100 --direction egress
./koc network qos rule list kocrev-qos
RULE=$(./koc network qos rule list kocrev-qos -f value -c ID | head -1)
./koc network qos rule show kocrev-qos $RULE
./koc network qos rule set kocrev-qos $RULE --max-kbps 2000
./koc network qos rule delete kocrev-qos $RULE
./koc network qos policy delete kocrev-qos
```

The things worth verifying here, in order of how likely they are to be wrong:

1. **`rule list` reads the rules off the policy**, not a per-type endpoint.
   Confirm the `Properties` column shows the rule's actual settings
   (`max_kbps=1000, …`) and that a rule of a type `koc` does not model still
   appears with its settings rather than vanishing.
2. **`show`/`set`/`delete` discover the rule's type from the policy** before
   choosing an endpoint. With `--debug`, confirm `set` on a bandwidth-limit rule
   goes to `/bandwidth_limit_rules/<id>` and that no `--type` flag was needed.
3. **A set sends only its own type's attributes.** `--max-kbps` on a
   dscp-marking rule must be ignored, not 400.
4. **`policy set --no-share` sends `shared: false`**, not nothing.
5. If this cloud is 2023.1 or newer, test `--type minimum-packet-rate` too —
   that is the type gophercloud has no package for and the reason the rule verbs
   use a raw path.

## §8 — Baremetal (24 commands) — only if ironic is present

`baremetal node adopt/clean/rescue/unrescue/service/unhold/validate/inject nmi`,
`baremetal node vif list/attach/detach`, `baremetal node bios setting list/show`,
`baremetal node firmware list`, `baremetal allocation ×6`,
`baremetal conductor show`, `baremetal driver property list`,
`baremetal driver raid property list`.

**Provision-state verbs move real hardware.** Run them only against a node you
are allowed to break, and record the node's starting `provision_state` so you can
put it back.

Start with the reads, which are safe:

```sh
./koc baremetal node validate <node>
./koc baremetal node vif list <node>
./koc baremetal node bios setting list <node>
./koc baremetal node bios setting show <node> <setting-name>
./koc baremetal driver property list <driver>
./koc baremetal driver raid property list <driver>
./koc baremetal conductor show <hostname>
```

`bios setting show` is a fixed gophercloud bug: ironic keys the response by the
**setting's own name** (`{"BootMode": {…}}`), and the upstream decoder looks for
a `"Setting"` key, silently returning a zero value. A blank result here means the
fix regressed.

Microversion-gated verbs — each must fail with a message naming the required
version on an older cloud, and work on a newer one:

```sh
./koc baremetal node unhold <node>          # ironic 1.85 (2023.2)
./koc baremetal node firmware list <node>   # ironic 1.86 (2023.2)
./koc baremetal node service <node> --service-steps <file>   # ironic 1.87 (2023.2)
```

On a Zed cloud (max 1.82) all three must explain the requirement rather than
report "no such node" — ironic answers 404 for an unknown route, which is
indistinguishable from a missing node unless the guard speaks up. This is the
single most important check in this section.

```sh
./koc baremetal allocation create --resource-class <rc> --name kocrev-alloc --wait
./koc baremetal allocation list
./koc baremetal allocation show kocrev-alloc
./koc baremetal allocation set kocrev-alloc --name kocrev-alloc2
./koc baremetal allocation unset kocrev-alloc2 --name
./koc baremetal allocation delete kocrev-alloc2
```

`allocation create --wait` polls to `active` and must fail with the API's
`last_error` — not a timeout — when the allocation goes to `error`. Force that
by requesting a resource class no node has.

`allocation set/unset` use an RFC 6902 patch (gophercloud has no Update); check
with `--debug` that the ops are `replace`/`remove` on the right paths.

Provision verbs, on a sacrificial node only:

```sh
./koc baremetal node clean <node> --clean-steps <file> --wait
./koc baremetal node clean <node> --runbook <runbook>   # ironic 1.92
./koc baremetal node rescue <node> --rescue-password <pw> --wait
./koc baremetal node unrescue <node> --wait
./koc baremetal node adopt <node> --wait
./koc baremetal node inject nmi <node>
```

`--clean-steps`/`--service-steps` accept a file, `-` for stdin, or an inline
JSON/YAML string. Test all three forms — the parser accepts JSON as a YAML
subset, and a regression there would only show on one of them.

## §9 — Report format

Produce one table, then the detail:

| # | Command | Verdict | Note |
| --- | --- | --- | --- |
| 1 | `network qos rule set` | PASS | matches `openstack` byte-for-byte |
| 2 | … | FAIL | 400: neutron wants `max_burst_kbps`, koc sends `max_burst_kbits` |
| 3 | … | BLOCKED | `rbac-policies` extension not enabled |

Verdicts: **PASS** (works and the output is right), **FAIL** (wrong request,
wrong output, or a crash), **BLOCKED** (the cloud cannot answer — extension
absent, service absent, no second project), **SKIPPED** (too destructive for this
cloud; say so).

Then, for each FAIL:

- the command line, with private values replaced by placeholders;
- what `koc` sent (`--debug`, hostnames redacted) and what came back;
- what upstream `openstack` sends for the same request, if it is installed;
- your read on whether the bug is in the flag surface, the request body, the
  output layer, or the microversion guard.

Close with:

1. **The cloud's release and per-service microversion ceilings**, so every
   verdict above can be scoped.
2. **Any command that behaved differently from upstream OSC** even where both
   "worked" — divergence is the thing this project is trying not to ship.
3. **A recommended fix order**, worst-first. Do not write the fixes in this
   session.
